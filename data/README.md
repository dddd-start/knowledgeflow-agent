# data/ —— 企业知识库智能问答的数据资产

本目录是「企业知识库智能问答」演示项目的数据层，包含 **知识库语料**、**检索评测集**、**拒答评测集** 与 **意图分类数据集**。

## 数据来源与声明

- 全部语料、评测题、意图样本均为 **人工原创撰写 / 人工设计模板组合生成**，不来自任何真实公司的内部资料，也不包含真实公司名称、真实个人信息。
- 文中出现的公司「**云策科技**」及其产品「**云策 OA**」、客户名称、版本号、金额与时限均为虚构设定，仅用于演示与评测。
- 原 `data/raw/` 的 5 篇样例文档已全部改写：`费用报销流程` 由人事类移到财务类并按新口径扩写；`账号与登录常见问题` 合并进 `IT服务-账号与权限管理` 的 FAQ 小节；其余 3 篇（考勤、OA 简介、私有化部署）在保留原结构的基础上补齐数字、流程与表格。
- 数据面向三类用途：
  1. **演示**：让 Demo 里的知识库问答有足够真实的中文企业文档可检索；
  2. **评测**：量化检索（Top-1 / Recall@3/5 / MRR）、意图分类（Top-1 准确率）与拒答（幻觉自检）效果；
  3. **回归**：改动分块、检索、重排、提示词后，用同一批题对比 before/after。

## 一、知识库语料（data/raw/）

### 命名与格式约定

- 文件名格式：`类别-标题.md`，例如 `财务制度-费用报销流程.md`。
- **doc_id 规则**：`doc-` + 文件名去掉 `.md`，例如 `doc-财务制度-费用报销流程`。检索评测集与 `kb_search` 工具的 doc_id 均以此为准。
- 每篇含 YAML front matter（`category`、`title`）+ 一级标题 `# 标题` + 若干二级小节 `## 小节名`，正文为短段落、列表与 Markdown 表格。
- 每篇 800–1800 字（按中文字符统计，实际 805–1086 字），尽量包含具体数字、时限、审批层级与责任人，便于出有区分度的评测题。

### 类别与文档清单

| 类别 | 篇数 | 文档 |
| --- | --- | --- |
| 人事制度 | 4 | 考勤管理制度、请假与休假制度、入职与试用期管理、员工培训与学习发展 |
| 财务制度 | 3 | 费用报销流程、差旅标准与出差申请、采购与合同审批 |
| IT服务 | 3 | 账号与权限管理、VPN 与远程接入、打印机与办公设备 |
| 产品手册 | 3 | 云策 OA 平台简介、版本发布说明、客服支持与工单规范 |
| 技术文档 | 3 | 私有化部署指南、发布与回滚流程、接口与 API 接入说明 |
| 安全合规 | 3 | 数据分级与保护规范、信息安全事件应急预案、终端与密码安全规范 |

语料按同一套虚构制度编写，关键数字在各文档之间保持一致，避免检索评测出现「两个都答得对」的歧义：

| 报销打款 | 每月 5 日、20 日两批，节假日顺延 | 费用报销流程、采购与合同审批 |
| 报销时限 | 费用发生后 30 天内提交 | 费用报销流程、差旅标准与出差申请 |
| 住宿标准 | 一线 600 / 新一线 450 / 其他 350 元每晚 | 差旅标准与出差申请、费用报销流程 |
| 考勤 | 10:00–19:00，弹性 09:30–10:30，核心时段 14:00–18:00；每月 3 次补卡 | 考勤管理制度、请假与休假制度 |
| 年假 | 满 1 年 5 天，每年 +1，上限 15 天 | 请假与休假制度、入职与试用期管理 |
| 账号 | 密码 90 天更换、12 位起、连续 5 次错误锁定 15 分钟、最多 2 台设备 | 账号与权限管理、终端与密码安全规范 |

| 发布 | 周二 / 周四 14:00–18:00，需求冻结周四 18:00，回滚 SLA 15 分钟 | 发布与回滚流程、版本发布说明 |
| 数据分级 | L1–L4；L3 导出双签，L4 不出内网；操作日志保留 180 天 | 数据分级与保护规范、云策 OA 平台简介 |

## 二、检索评测集（data/eval/eval_queries.json）

40 条人工标注的问题，每条字段：

| 字段 | 含义 |
| --- | --- |
| `query` | 用户问题，口语化表达为主 |
| `gold_doc` | 正确文档的 doc_id，必须精确存在于 `data/raw/` |
| `note` | 考察点：考的是哪条事实、哪类难点 |
| `type` | 题型：`keyword` / `paraphrase` / `multi_hop` / `noisy` |

### 题型分布

| 类型 | 条数 | 设计意图 |
| --- | --- | --- |
| `keyword` | 14 | 关键词直球，检验基础检索与分块质量；Top-1 应稳定命中 |
| `paraphrase` | 16 | 口语化 / 同义改写，问题里不出现原文关键词，检验向量语义检索与 HyDE、查询改写 |
| `multi_hop` | 6 | 需要跨段落或跨两篇文档取信息，检验多段拼装与重排 |
| `noisy` | 4 | 长问题里混入无关信息，检验查询改写与噪声鲁棒性 |
| 合计 | 40 | 覆盖全部 19 篇文档，每篇至少 1 条 |

### 评测方法

- 指标：Top-1 准确率（命中 `gold_doc`）、Recall@3 / Recall@5、MRR；
- 对比方式：纯向量 vs BM25 vs 混合检索 vs 混合 + 重排 vs 全链路（查询改写 + HyDE），同一批题反复跑；
- 结果解读：小样本（40 条）下指标波动大，结论应表述为「方法验证」，并说明扩样方向；
- 该文件字段与 `scripts/eval_retrieval.py` 的读取约定一致：`query` + `gold_doc`。

## 三、拒答评测集（data/eval/oos_queries.json）

12 条「知识库覆盖不到」的问题，每条字段 `query` / `note` / `expected`，`expected` 固定为 `refuse`。覆盖六类不可答场景：

1. 未公开的公司经营数据（如股价）；
2. 竞品内部数据；
3. 实时动态数据（如天气），应由工具而非知识库回答；
4. 外部时事常识；
5. 个人隐私与客户敏感凭据（手机号、数据库密码、他人工资）；
6. 知识库未规划的产品信息（如 4.0 版本）。

评测口径：正确行为是明确说明「知识库中没有相关信息 / 无法提供」，并给出可行的替代路径（走工具、联系某人），**不得编造看似合理的数字或条款**。该集用于统计拒答率与幻觉率，建议与 `eval_queries.json` 一起跑，避免「为了拒答而把所有问题都拒掉」。

## 四、意图分类数据集（data/intents/）

### 文件与字段

- `train.json`、`eval.json`：每条为 `{"text": "...", "intent": "..."}`，按 `labels.json` 中的类别顺序分组排列；
- `labels.json`：6 个类别的 `id` / `name` / `desc`（同时保留 `label`、`description`、`handler` 兼容字段），`desc` 明确写清每个类别的边界与相邻类别的区别。

| intent id | 名称 | 条数（train） | 条数（eval） | 路由去向 |
| --- | --- | --- | --- | --- |
| weather | 天气查询 | 110 | 22 | `fast_tool:get_weather` |
| calculator | 数学计算 | 110 | 22 | `fast_tool:calculator` |
| datetime | 日期时间 | 110 | 22 | `fast_tool:get_datetime` |
| kb_query | 知识库查询 | 110 | 22 | `rag` |
| small_talk | 闲聊 | 110 | 22 | `chat` |
| complex_agent | 复杂任务 | 110 | 22 | `agent` |
| 合计 | | **660** | **132** | |

### 设计说明

- **均衡**：训练集与评测集 6 类严格等量，避免小样本分类器偏科；
- **口语化、长度多样**：从 2 字（「嗨」「多谢」）到 40 字的多步请求都有，符合真实聊天分布；
- **易混样本**（刻意构造，用于检验边界，而不是制造噪声）：
  - `datetime` vs `kb_query`：「现在几点」「今天几号」属于时钟；「上班时间是几点」「打款是每月几号」「发布窗口是周几」属于知识库；
  - `weather` vs `kb_query`：「北京今天天气怎么样」属于天气工具；「北京出差住宿标准」属于知识库；
  - `calculator` vs `kb_query`：「帮我算一下 128 乘以 7」属于计算；「报销 15000 元要谁审批」属于知识库；
  - `small_talk` vs `complex_agent`：「在吗」属于闲聊；「在吗，先查天气再算报销审批」属于复杂任务；
  - `kb_query` vs `complex_agent` 的边界：能否一次检索答完——需要多工具、多子任务或检索 + 计算的归 `complex_agent`。
- **数据卫生**：训练集与评测集**无重复、无重叠**（脚本已断言），评测集不参与训练；
- **生成方式（如实说明）**：意图样本由人工设计的句式模板 + 槽位词表（城市、算式、制度问题、寒暄短语）组合生成，再人工抽检与去重，不是逐条手写；语料与两个评测集的题目均为人工逐条撰写。若要进一步提升自然度，可在保持类别与条数不变的前提下继续人工替换部分样本。

## 五、如何扩展

### 增加知识库文档

1. 在 `data/raw/` 新建 `类别-标题.md`，类别必须是上面 6 个之一，标题避免与已有文档重复；
2. 保持 front matter、`#` / `##` 结构与 800–1800 字规模；
3. 涉及金额、时限、审批层级时，先查本文档「跨文档一致性口径」表，同步更新相关文档；
4. 重新入库（按项目根 README 的步骤重建索引），doc_id 会自动变为 `doc-<文件名去.md>`。

### 增加检索评测题

1. 在 `eval_queries.json` 追加条目，`gold_doc` 必须能在 `data/raw/` 找到；
2. 保持题型配额（keyword 14 / paraphrase 16 / multi_hop 6 / noisy 4 的比例），扩样时按比例同步扩充；
3. `note` 写清考什么，便于复盘时判断是「检索没召回」还是「分块切坏了」。

### 增加意图样本

1. 在 `train.json` / `eval.json` 追加 `{"text","intent"}`，并保持 6 类近似均衡；
2. 新样本必须与评测集去重，且不要跨集复用；
3. 新增类别时同步更新 `labels.json`（`id` 顺序即分类器的输出顺序）。

### 自检（修改数据后建议执行）

```bash
cd knowledgeflow-agent
python3 -c "
import json,glob,os,collections
q=json.load(open('data/eval/eval_queries.json',encoding='utf-8'))
o=json.load(open('data/eval/oos_queries.json',encoding='utf-8'))
t=json.load(open('data/intents/train.json',encoding='utf-8'))
e=json.load(open('data/intents/eval.json',encoding='utf-8'))
docs={os.path.splitext(os.path.basename(f))[0] for f in glob.glob('data/raw/*.md')}
print('docs',len(docs),'eval',len(q),collections.Counter(x['type'] for x in q))
print('oos',len(o),'train',len(t),'eval_intent',len(e))
print('missing gold',[x['gold_doc'] for x in q if x['gold_doc'][4:] not in docs])
print('intent dup', len(t)+len(e)-len({x['text'] for x in t+e}))
"
```
