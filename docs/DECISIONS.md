# 设计决策记录（ADR）

> 面试里最容易被追问的是"为什么"而不是"做了什么"。这里记录 9 个关键决策的**背景、备选方案、取舍和代价**。
> 格式：背景 → 决策 → 代价 → 什么情况下会推翻它。

---

## ADR-01 不用 LangChain 全家桶，只保留 LangGraph 级别的"显式编排"（实际是手写）

**背景**：RAG/Agent 生态默认答案是 LangChain，但链式抽象会把"检索到了什么、为什么这么回答"藏进黑盒，调试和讲解都很难。

**决策**：核心链路（分块、检索、融合、Agent 循环、记忆、自检）全部手写，只依赖 HTTP + numpy + jieba + rank_bm25 + sentence-transformers。全套业务代码约 3k 行，每一行都能在面试里解释。

**代价**：重复造轮子（如分块、工具注册表），少了生态里现成的回调/追踪。

**何时推翻**：需要接十几个数据源连接器、或团队已有 LangChain 规范时，手写维护成本会超过收益。

## ADR-02 默认 numpy 精确检索，而不是一开始就上向量数据库

**背景**：企业知识库的语料往往只有几千到几万个块，HNSW 这类 ANN 索引主要解决百万级以上的延迟问题。

**决策**：实现 `BaseVectorStore` 接口，默认 `NumpyVectorStore`（npy + json 持久化，精确余弦），保留 ChromaDB 实现，配置一行切换。

**代价**：单机内存占用随语料线性增长；向量检索是 O(N·d) 精确计算。

**何时推翻**：块数 > 50 万或需要按租户分区时切 Qdrant/Milvus；接口不变，只换实现。

---

## ADR-03 融合用 RRF，而不是加权分数相加

**背景**：向量余弦（0~1）与 BM25 分数（无上界、随语料变化）量纲完全不同，直接加权需要先归一化，而归一化本身不稳定（同一查询不同语料分布差异巨大）。

**决策**：RRF 只用名次：`score = Σ 1/(k+rank)`，k=60，支持通道权重（HyDE 通道 0.8）。不依赖分数尺度，几乎不需要调参。

**代价**：丢掉了"差距很大"的信息（第 1 名 0.9 与第 2 名 0.3 的区分度被压缩）；需要靠后续重排补回精度。

**何时推翻**：如果两路分数经过可靠校准（如统一到同一模型打分的 logits），学习型融合（如加权/学习排序）可能更优。

## ADR-04 检索优化"逐级消融、按数据决定去留"：默认关闭 HyDE 与重排

**背景**：查询改写 / HyDE / 重排是 RAG 的"标准三件套"，但标准不等于有效——它们的收益高度依赖语料与查询分布，且都有延迟成本。

**决策**：写评测脚本做消融（40 条人工评测集），按"Top-1 提升 / 延迟代价"决定默认值：
- 查询改写：+5pt，代价 ~0.9s → **默认开启**；
- HyDE：多花 ~2s，收益不稳定（两次运行分别在 0 与 +5pt 之间波动）→ **默认关闭，保留开关**；
- Cross-Encoder 重排：模型 1.1GB、每查询 +1.5s，收益见报告 → **默认关闭，按需开启**。

**代价**：默认配置不是"看起来最先进"的配置，需要向面试官解释"为什么不用"。

**何时推翻**：语料换成真实企业文档、查询更口语化时，需要重跑消融再定默认值（脚本已就绪）。

## ADR-05 意图分类用微调 TinyBERT，而不是让大模型判断

**背景**：简单意图（天气/计算/时间/寒暄）在真实流量里占比高，若每次都用大模型判意图，要多花 1~2s 和一次 token 成本。

**决策**：自建 6 类、660 条训练集 + 132 条评测集，微调 `TinyBERT_4L_zh`（11M 参数），CPU 单条 <10ms，准确率 96.2%；模型不可用时自动降级为规则分类器。

**代价**：意图体系变化需要重新标注与训练；存在分布外意图被强行归类的问题——用置信度阈值 + Agent 兜底缓解。

**何时推翻**：意图类别超过 20 个或需要多标签时，改成"小模型召回 + 大模型复核"或直接用大模型分类。

## ADR-06 SSE 事件流，而不是一次性 JSON 返回

**背景**：RAG 回答通常 2~8 秒，一次性返回会让用户盯着空白等待；而检索过程（改写、召回、融合）本身是有信息量的。

**决策**：`POST /api/chat` 默认 SSE，事件粒度：`meta → retrieval → delta* → citations → self_check → usage → done`。前端可以边生成边渲染，也能可视化检索链路。

**代价**：接口更复杂（要处理断线、`replace` 修订、事件顺序）；非流式调用方需要聚合（已提供 `stream=false` 与 `collect_events()`）。

**何时推翻**：面向服务端调用且不需要中间过程时，用普通 JSON 更省事（本项目两种都支持）。

## ADR-07 离线 Mock 是一等公民，不是测试专用桩

**背景**：面试演示最怕"现场没网/没 Key/模型下载失败"；CI 也不该依赖外部 API。

**决策**：`MockLLM` 是完整实现：能读懂 RAG 上下文生成带引用回答、能按 Function Calling 协议发起工具调用、能按 `purpose` 返回 judge/自检的结构化 JSON。`auto` 策略在缺 Key 时自动启用，页面明确标注"离线演示模式"。

**代价**：Mock 的行为需要与真实模型"形似"，维护成本；有"演示效果与真实效果不一致"的风险。

**何时推翻**：不需要对外演示、CI 也可以用录制回放替代时。

---

## ADR-08 配置的 `auto` 降级链：让 `git clone` 后零配置可运行

**背景**：任何需要"先配置 3 个环境变量才能启动"的项目，在面试现场都有翻车风险。

**决策**：所有外部依赖都有 `auto` 解析：LLM 无 Key → mock；无 ML 依赖 → 哈希向量；无 chromadb → numpy；重排模型不可用 → 跳过。索引维度与当前 embedding 不一致时自动重建。真实配置只需一个 `.env`。

**代价**：隐式降级可能让用户误以为用的是真实模型——用 `/api/meta` 与页面徽章显式标注当前后端来缓解。

**何时推翻**：生产环境应显式指定后端，禁止静默降级（fail fast）。

---

## ADR-09 Prompt 模板化 + 版本号 + 热加载

**背景**：RAG 的效果很大一部分由 prompt 决定，改 prompt 不应该改代码、不应该重启、更不应该"改了不知道改了什么"。

**决策**：全部 prompt 放 `app/prompts/templates/*.j2`，文件头带 `# prompt-version`，`PromptManager` 热加载 + 版本快照；trace 里记录本次请求用的 prompt 版本。

**代价**：模板与代码分离，IDE 跳转与类型检查变弱；模板变量缺失需要兜底（已用 SilentUndefined）。

**何时推翻**：prompt 需要复杂逻辑（多步组装、条件分支）时，用代码 + 模板混合更合适。
