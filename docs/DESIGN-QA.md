# 设计问答（Design Q&A）

> 这个文件把「为什么这么设计」集中记录成问答形式，覆盖检索、Agent、工程化、评测四块。
> 与 [DECISIONS.md](DECISIONS.md) 的区别：ADR 记录**决策的取舍与推翻条件**，这里回答**具体实现问题**（某段代码为什么这么写、参数为什么是这个值）。
> 所有数字以 `eval/report-*.json` 为准，脚本在 `scripts/`，可一键复现。

---

## 一、检索与 RAG

### Q1. 为什么用混合检索？只做向量不行吗？

- 向量擅长语义相近（「住酒店的钱怎么找公司要」↔「差旅住宿报销」），但对专有名词、编号、精确术语（「VPN-2024」「SLA 99.9%」「工号」）不敏感；
- BM25 正好相反：词面命中极准，但同义改写无能为力；
- 实测：paraphrase（口语化）类问题，纯 BM25 Top-1 只有 31.3%，向量 68.8%、混合+改写后 81.3%；而 keyword 类 BM25 反而更快更准。
- 融合方式见 Q2。

### Q2. RRF 是什么？为什么不用加权分数相加？

- 公式：`score(d) = Σ 1/(k + rank_d)`，k=60；
- 原因：余弦相似度是 0~1，BM25 分数无上界且随语料变化，量纲不可比；加权需要先归一化，而归一化对分布敏感、不稳定；
- 代价：丢掉了「第一名领先很多」的信息，所以后面留了重排的位置；
- 实现：`app/rag/hybrid.py`，支持通道权重（HyDE 通道 0.8）。

### Q3. 分块策略怎么选的？

- 实现了三种：固定窗口（简单、块大小可控）、递归（标题→段落→句子，边界落在语义处）、语义（句向量相邻相似度断点，慢）；
- 默认递归：块边界更自然，块内保留【小节标题】前缀，检索解释性更好；
- 实测（同一份语料、同一套检索）：fixed 80%、recursive 85%、semantic 77.5% —— 语义分块在短文档上反而更差，因为切出来的块太小、上下文变碎，所以没用；
- 块大小 500 字、重叠 60 字；再大上下文噪声多，再小一句话被拆散。

### Q4. 查询改写解决了什么问题？

- 多轮对话里的指代（「那它要多久」）、口语化（「住酒店的钱找公司要」）导致检索词与文档用词不匹配；
- 用 LLM 改写成独立、书面化的检索查询，实测 Top-1 85% → 90%（paraphrase 类 62.5% → 81.3%）；
- 失败兜底：输出为空/太长/解析失败就回退原查询；`temperature=0` 保证可复现。

### Q5. HyDE 是什么？为什么默认关掉？

- HyDE：让 LLM 先写一段「假设答案文档」，用它向量化去检索，拉近 query 与文档的向量距离；
- 实测多花约 3s，Top-1 从 90% 到 92.5%，收益与代价不匹配；
- 与改写并发执行（两者互不依赖），省一轮 RTT；
- 原则：先量化再决定，不因为「业界都说好」就默认开启；开关保留（`HYDE_ENABLED`），换语料可重跑消融。

### Q6. 重排为什么默认关闭？Cross-Encoder 和向量检索什么区别？

- 向量是双塔（bi-encoder）：query 和 doc 分别编码，快但精度有上限；Cross-Encoder 把 (query, doc) 拼起来一起过模型，能建模细粒度交互，准但慢（每题 N 次前向）；
- 实测在本语料上重排把 Top-1 从 92.5% 降到 90%，且每查询 +3.3s、模型 1.1GB；
- 结论：做成开关（`RERANK_ENABLED=true` 可开），评测脚本支持对比（`--rerank`）。

### Q7. 中文 BM25 要注意什么？

- 必须分词：rank_bm25 不做分词，中文按空格拆，「费用报销」会变成生词，检索效果接近 0；
- 用 jieba 的 `lcut_for_search`（搜索引擎模式），长词再切一次提高召回；
- 小语料坑：语料只有 2 篇时 IDF 可能为负，直接过滤负分会「明明命中却返回空」，所以实现里做了正分优先、无正分时按分数兜底。

### Q8. 向量库为什么用 numpy 而不是 Chroma/Milvus？

- 语料规模 75 块，精确余弦单次 p50 17ms；ANN 索引（HNSW）在这个规模下延迟收益可忽略，还多一套组件要运维；
- 做了 `BaseVectorStore` 接口 + Chroma 实现，配置一行切换；块数上到几十万再换；
- 各阶段 P50/P95 见 `scripts/bench.py`。

### Q9. 引用是怎么保证可溯源的？

- 检索命中块带 `doc_id`、标题、块序号、字符位置；拼接上下文时编号 `[1]`…；prompt 要求每条结论标注编号；
- 前端把 `[n]` 和 citations 列表联动，点一下高亮原文片段；
- 自检环节也会核对「结论是否有证据」，编造的无依据内容会被判 unsupported。

### Q10. 文档更新了怎么增量入库？

- 单篇覆盖：先按 `doc_id` 删除旧块、重新分块向量化，再重建 BM25（小语料全量重建，秒级）；
- 全量重建：`POST /api/kb/reindex`；
- 索引原子写（临时文件 + rename），进程被杀不会留半个索引；
- 换 embedding 模型导致维度不一致时，启动自动检测并重建，不会静默出错。

## 二、Agent 与工具调用

### Q11. Agent 循环怎么实现的？

- OpenAI Function Calling 协议：模型返回 `tool_calls` → assistant 消息原样带回 → 逐个执行 → 以 `role=tool` + `tool_call_id` 回填 → 直到不再请求工具；
- 最多 3 轮（`MAX_AGENT_ROUNDS`），到上限时禁用工具、加一句「请基于已有信息收敛」，强制出答案；
- 工具异常在注册表层转成 `is_error=True` 的文本，模型可自我修正，不会打断请求。

### Q12. 为什么是 5 个工具？

- `kb_search` + `kb_read`：Search/Read 分工，先检索片段，不够再读全文，模仿人查文档；
- `calculator` / `get_datetime`：确定性能力，交给模型算容易错，工具化更可靠；
- `get_weather`：代表外部 API（用本地样例数据，接口形态与真实 API 一致）；
- 工具多了会怎样：工具描述占满上下文、选择变难，所以控制在 5 个并写清楚使用边界。

### Q13. 工具安全怎么做的？

- calculator 用 AST 白名单求值（只允许四则/取模/括号），禁用 `**` 和函数调用，空 builtins 环境执行——不用 eval 原样执行；
- 参数校验：required/type/enum，在注册表层做，模型传错直接返回错误文本；
- 超时：线程池 + `future.result(timeout)`，工具卡死不会拖垮请求；
- 输出截断：防止一次工具调用把上下文打爆。

### Q14. 什么情况下会走 Agent 而不是 RAG？

- 意图置信度低于阈值（默认 0.6）、意图是 `complex_agent`（对比/分析/多步骤）、或规则明显判断不了时；
- 原则：规则不要拦死复杂问题，低置信度永远有 Agent 兜底。

### Q15. Agentic RAG 和 Agent 有什么区别？

- Agent 是「调工具」的循环（可能调计算器、时间、知识库）；
- Agentic RAG 是「检索策略」的循环：检索 → judge 证据是否充分 → 不足则带着「缺什么」改写查询再检索；
- 典型场景：多跳问题（「住宿标准是多少 + 超标怎么审批」），一次检索只覆盖一半；
- 停止条件：证据充分或达到 3 轮上限（`AGENTIC_MAX_ROUNDS`），上限时用最后一轮证据诚实作答。

## 三、工程与架构

### Q16. 一次请求的完整链路？

- 记忆维护（压缩/话题检测）→ 意图路由 → 检索（改写/双路召回/RRF/可选重排）→ 生成（SSE 流式）→ 自检 → 记忆写回 → 事件流结束；
- 每个阶段都记耗时和中间结果，前端可视化，评测脚本可导出。

### Q17. 为什么用 SSE 而不是 WebSocket？

- 需求是单向流式（服务端→浏览器），SSE 基于 HTTP，天然支持断线重连、经过 nginx 只需关缓冲；
- WebSocket 是双向长连接，运维和鉴权更复杂，这里没有双向需求；
- 部署注意：nginx 需要 `proxy_buffering off`，否则会攒着一次性吐。

### Q18. 降级链怎么设计的？

- 没有 Key → Mock LLM；没有 ML 依赖 → 哈希向量；没有 chromadb → numpy；重排不可用 → 跳过；
- 网关 4xx/5xx/超时 → 指数退避重试 → 仍失败降级 Mock；
- 页面和 `/api/meta` 明确标注当前后端，不假装是真实模型；
- 生产环境建议 fail fast，不要静默降级（见 ADR-08）。

### Q19. 并发和性能上做了什么？

- 模型/索引进程级单例，启动预热（embedding/jieba/意图分类器），避免首个请求承担加载；
- 检索是 CPU 计算 + 外部 LLM 调用，FastAPI 用线程池跑同步逻辑，SSE 不阻塞事件循环；
- 改写与 HyDE 并发执行，省一轮 RTT；
- 单 worker 部署（模型常驻内存约 600MB），横向扩展建议把 embedding 拆成独立推理服务。

### Q20. 怎么保证「线上跑的和评测跑的是同一套逻辑」？

- 编排只有一份 `ChatService.answer()`，API、CLI、评测脚本都走它；
- 评测脚本用真实检索与真实 prompt，不另写一套；
- prompt 有版本号，trace 里记录本次用的版本。

## 四、评测与数据

### Q21. 评测集怎么建的？

- 40 条检索问题，按 type 分 keyword 14 / paraphrase 16 / multi_hop 6 / noisy 4，每条标 `gold_doc`；12 条库外问题用于拒答评测；
- 语料是 19 篇原创企业文档（虚构公司「云策科技」），数字跨文档自洽（报销阈值、住宿标准、发布窗口……）；
- 局限：自建小评测集，结论需要真实语料复核——但方法和脚本可直接复用。

### Q22. 消融怎么做？

- 固定同一份评测集与同一套 chunk，逐级叠加：BM25 → 向量 → 混合 → 改写 → HyDE → 重排；分块策略单独一组；
- 指标：文档级 Top-1/Top-3/MRR + 延迟分位；端到端另外看引用命中率、拒答率、token 成本；
- 详见 [EVALUATION.md](EVALUATION.md)。

### Q23. 怎么衡量「幻觉」？

- 构造 12 条知识库覆盖不到的问题（股价、竞品、隐私、未发布版本）；
- 正确行为是拒答，统计拒答率；同时看 in-scope 问题有没有被误拒（误杀率）；
- 自检是独立 judge + 证据，不是让模型自查。

### Q24. 有哪些数据能证明效果？

- 检索：Top-1 62.5%（BM25）→ 90%（混合+改写）；
- 分块：fixed 80% / recursive 85% / semantic 77.5%；
- 意图：96.2% 准确率（规则基线 59.9%），CPU 单条预热后约 8ms（首次调用含模型加载约 60ms）；
- 端到端：P50/P95 延迟、平均 token、单次成本见 `eval/report-e2e.json`；
- 测试：103 个离线用例全绿，CI 可复现。

## 五、取舍与反思

### Q25. 这个项目最大的难点是什么？

- 不是某个算法，而是**把「能不能用」变成「可证明好用」**：检索参数、prompt、分块、重排每一个都可以说「我调好了」，但只有建评测集才能说清「好在哪、代价是什么」；
- 第二是**一致性**：一次问答涉及 5~6 个组件，任何一处降级或口径不同都会让评测失真，所以统一编排 + 统一 trace。

### Q26. 如果重做，会改什么？

- 评测集扩大 + 引入真实企业语料，做统计显著性检验（现在 40 条，Top-1 差 2.5pt 不可靠）；
- 检索层做语义缓存（相似问题复用），能显著降本；
- embedding/rerank 拆成独立推理服务，支持多副本；
- 文档解析补 PDF 版面分析（表格、扫描件）。

### Q27. 为什么不用 LangChain？

- 链式抽象把「检索到了什么、为什么这么答」藏进黑盒，调试和讲解困难；
- 手写 `app/` 约 5.7k 行业务代码，每一行都能解释；只用了 HTTP、numpy、jieba、rank_bm25、sentence-transformers；
- 代价：重复造轮子，生态里的回调/追踪能力要自己实现（已用 trace 补上）。

### Q28. 为什么用 Python 而不是 Java？

- AI 生态（模型、检索、评测工具）在 Python 侧最完整，验证想法最快；
- 架构刻意做成语言无关的：检索/Agent/评测的逻辑与 IO 解耦，换 Java 只需换 HTTP 与模型客户端层；
- 用 Python 是为了快速验证算法侧，不代表工程能力的取舍——部署、CI、测试、可观测性按生产标准做。

### Q29. 迁移到生产环境要补什么？

| 方面 | 当前实现 | 生产要补 |
| --- | --- | --- |
| 检索 | numpy 精确检索，75 块 | 向量库换 Qdrant/Milvus，按租户分区 |
| 入库 | 同步一键重建 | 异步任务队列 + 增量更新 + 版本化 |
| 模型 | 单实例进程内加载 | embedding/rerank 独立推理服务，多副本 |
| 权限 | 无（单租户） | 多租户隔离、文档级 ACL、审计日志 |
| 降级 | 静默降级 Mock | fail fast + 告警，禁止静默降级 |
| 评测 | 离线脚本 | 线上抽样回流 + 人工标注闭环 |

### Q30. 怎么把项目经验迁移到新场景？

以「研发上下文知识库」为例：

- 三类异构数据分开处理：文档（制度/设计稿）走文本分块 + RAG；代码走函数/类粒度索引（可加代码图谱）；日志/告警走时序检索；
- 分层检索：高频问答 RAG；跨文件关系用代码图谱；日志按时间窗检索；
- 统一路由层：先判断问题类型，再选检索器——复用本项目的意图路由思想；
- 质量闭环：入库抽检 + 检索命中率回灌 + 低置信度样本进迭代清单。
