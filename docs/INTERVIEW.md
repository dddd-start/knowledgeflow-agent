## 一、电梯演讲（3 分钟，背下来）

> "我做一个企业知识库智能问答系统，叫 KnowledgeFlow。
>
> **背景**：公司制度、流程、产品文档散落在 wiki 里，员工查资料慢；直接套通用大模型会有两个问题——检索不准、而且会编造公司规定。
>
> **我做了什么**：从 0 独立实现了一套完整链路。检索侧是向量 + BM25 双路召回、RRF 融合，再加上查询改写和可选的重排；服务侧先做意图路由，天气、计算、时间这类简单问题 0 次大模型直接走工具，知识库问题走 RAG，复杂多跳问题走 Agentic 迭代检索；生成之后还有一道独立的事实核查，证据支持不了就拒答。
>
> **工程上**：FastAPI + SSE 流式，前端能把检索的每个阶段、候选片段、分数、耗时实时画出来；100 个离线测试、CI、Docker 一键起；没有 API Key 也能用确定性 Mock 跑完整链路，面试演示不怕断网。
>
> **结果**：我自建了 40 条检索评测集做消融——纯 BM25 Top-1 是 62.5%，混合检索 85%，加查询改写 90%；意图分类微调 TinyBERT 到 96.2%，CPU 单条约 50ms（规则基线 59.9%）；HyDE 和重排我也测了，收益不稳定或为负，所以默认关闭，理由和数字都写在仓库的评测报告里。
>
> 这个项目是我空窗期的主要产出，代码、评测、文档都在 GitHub 上。"

**一句话版**："一个可评测、可解释、离线也能演示的企业知识库 RAG Agent。"

## 二、高频深挖题（30 道）

### A. 检索与 RAG

**A1. 为什么用混合检索？只做向量不行吗？**
- 向量擅长语义相近（"住酒店的钱怎么找公司要" ↔ "差旅住宿报销"），但对专有名词、编号、精确术语（"VPN-2024"、"SLA 99.9%"、"工号"）不敏感；
- BM25 正好相反：词面命中极准，但同义改写无能为力；
- 实测：paraphrase（口语化）类问题，纯 BM25 Top-1 只有 31%，向量 69%、混合+改写后 81%；而 keyword 类 BM25 反而更快更准。
- 追问"融合怎么做的"：RRF，按名次不按分数，见 A2。

**A2. RRF 是什么？为什么不用加权分数相加？**
- 公式：`score(d) = Σ 1/(k+rank_d)`，k=60；
- 原因：余弦相似度是 0~1，BM25 分数无上界且随语料变化，量纲不可比；加权需要归一化，而归一化对分布敏感、不稳定；
- 代价：丢掉了"第一名领先很多"的信息，所以后面留了重排的位置；
- 实现细节：`app/rag/hybrid.py`，支持通道权重（HyDE 通道 0.8）。

**A3. 分块策略怎么选的？**
- 实现了三种：固定窗口（简单、块大小可控）、递归（标题→段落→句子，边界落在语义处）、语义（句向量相邻相似度断点，慢）；
- 默认递归：块边界更自然，块内保留【小节标题】前缀，检索解释性更好；
- 实测（同一份语料、同一套检索）：fixed 80%、recursive 85%、semantic 77.5% —— 语义分块在短文档上反而更差，因为切出来的块太小、上下文变碎，所以没用；
- 追问"块大小"：500 字、重叠 60 字；再大上下文噪声多，再小一句话被拆散。

**A4. 查询改写解决了什么问题？**
- 多轮对话里的指代（"那它要多久"）、口语化（"住酒店的钱找公司要"）导致检索词与文档用词不匹配；
- 用 LLM 改写成独立、书面化的检索查询，实测 Top-1 85% → 90%；
- 有失败兜底：输出为空/太长/解析失败就回退原查询；temperature=0 保证可复现。

**A5. HyDE 是什么？为什么你默认关掉它？**
- HyDE：让 LLM 先写一段"假设答案文档"，用它向量化去检索，拉近 query 与文档的向量距离；
- 实测多花 ~3s，Top-1 只从 90% 提升到 92.5%，收益与代价不匹配；
- 原则：先量化再决定，不因为"业界都说好"就默认开启；开关保留，换语料可以重跑消融。

**A6. 重排为什么默认关闭？Cross-Encoder 和向量检索什么区别？**
- 向量是双塔（bi-encoder）：query 和 doc 分别编码，快但精度有上限；Cross-Encoder 把 (query, doc) 拼起来一起过模型，能建模细粒度交互，准但慢（每题 N 次前向）；
- 实测在本语料上重排把 Top-1 从 92.5% 拉到 90%（更差），且每查询 +1.5s、模型 1.1GB；
- 结论：做成开关，`RERANK_ENABLED=true` 可开；评测脚本支持对比（`--rerank`）。

**A7. 中文 BM25 要注意什么？**
- 必须分词：rank_bm25 不做分词，中文按空格拆，"费用报销"会变成生词，检索效果接近 0；
- 用 jieba 的 `lcut_for_search`（搜索引擎模式），长词再切一次提高召回；
- 小语料坑：语料只有 2 篇时 IDF 可能为负，直接过滤负分会"明明命中却返回空"，所以实现里做了正分优先、无正分时按分数兜底。

**A8. 向量库为什么用 numpy 而不是 Chroma/Milvus？**
- 语料规模 75 块（评测集 7.5 万块以内），精确余弦单次 <15ms；ANN 索引（HNSW）在这个规模下延迟收益可忽略，还多一套组件要运维；
- 做了 `BaseVectorStore` 接口 + Chroma 实现，配置一行切换；块数上到几十万再换；
- 追问"怎么证明"：`scripts/bench.py` 有各阶段 P50/P95。

**A9. 引用是怎么保证可溯源的？**
- 检索命中块带 `doc_id`、标题、块序号、字符位置；拼接上下文时编号 `[1]`…；prompt 要求每条结论标注编号；
- 前端把 `[n]` 和 citations 列表联动，点一下高亮原文片段；
- 自检环节也会核对"结论是否有证据"，编造的无依据内容会被判 unsupported。

**A10. 文档更新了怎么增量入库？**
- 单篇覆盖：先按 `doc_id` 删除旧块、重新分块向量化，再重建 BM25（小语料全量重建，秒级）；
- 全量重建：`POST /api/kb/reindex`；
- 索引原子写（临时文件 + rename），进程被杀不会留半个索引；
- 换 embedding 模型导致维度不一致时，启动自动检测并重建，不会静默出错。

### B. Agent / 工具调用

**B1. Agent 循环怎么实现的？**
- OpenAI Function Calling 协议：模型返回 `tool_calls` → assistant 消息原样带回 → 逐个执行 → 以 `role=tool` + `tool_call_id` 回填 → 直到不再请求工具；
- 最多 3 轮，到上限时禁用工具、加一句"请基于已有信息收敛"，强制出答案；
- 工具异常在注册表层转成 `is_error=True` 的文本，模型可自我修正，不会打断请求。

**B2. 为什么给 Agent 5 个工具？**
- `kb_search` + `kb_read`：Search/Read 分工，先检索片段，不够再读全文，模仿人查文档；
- `calculator` / `get_datetime`：确定性能力，交给模型算容易错，工具化更可靠；
- `get_weather`：代表外部 API（演示用本地数据，接口形态与真实 API 一致）；
- 追问"工具多了会怎样"：工具描述占满上下文、选择变难，所以控制在 5 个并写清楚使用边界。

**B3. 工具安全怎么做的？**
- calculator 用 AST 白名单求值（只允许四则/取模/括号），禁用 `**` 和函数调用，空 builtins 环境执行——不用 eval 原样执行；
- 参数校验：required/type/enum，在注册表层做，模型传错直接返回错误文本；
- 超时：线程池 + `future.result(timeout)`，工具卡死不会拖垮请求；
- 输出截断：防止一次工具调用把上下文打爆。

**B4. 什么情况下会走 Agent 而不是 RAG？**
- 意图置信度低于阈值（0.6）、意图是 complex_agent（对比/分析/多步骤）、或规则明显判断不了时；
- 原则：规则不要拦死复杂问题，低置信度永远有 Agent 兜底。

**B5. Agentic RAG 和 Agent 有什么区别？**
- Agent 是"调工具"的循环（可能调计算器、时间、知识库）；
- Agentic RAG 是"检索策略"的循环：检索 → judge 证据是否充分 → 不足则带着"缺什么"改写查询再检索；
- 典型场景：多跳问题（"住宿标准是多少 + 超标怎么审批"），一次检索只覆盖一半；
- 停止条件：证据充分或达到 3 轮上限，上限时用最后一轮证据诚实作答。

### C. 工程与架构

**C1. 一次请求的完整链路？**
- 记忆维护（压缩/话题检测）→ 意图路由 → 检索（改写/双路召回/RRF/可选重排）→ 生成（SSE 流式）→ 自检 → 记忆写回 → 事件流结束；
- 每个阶段都记耗时和中间结果，前端可视化，评测脚本可导出。

**C2. 为什么用 SSE 而不是 WebSocket？**
- 需求是单向流式（服务端→浏览器），SSE 基于 HTTP，天然支持断线重连、经过 nginx 只需关缓冲；
- WebSocket 是双向长连接，运维和鉴权更复杂，这里没有双向需求；
- 追问"nginx 要注意什么"：`proxy_buffering off`，否则会攒着一次性吐。

**C3. 降级链怎么设计的？**
- 没有 Key → Mock LLM；没有 ML 依赖 → 哈希向量；没有 chromadb → numpy；重排不可用 → 跳过；
- 网关 4xx/5xx/超时 → 指数退避重试 → 仍失败降级 Mock；
- 页面和 `/api/meta` 明确标注当前后端，不假装是真实模型；
- 追问"生产也能这样吗"：生产应 fail fast，禁止静默降级（ADR-08 写了）。

**C4. 并发和性能上做了什么？**
- 模型/索引进程级单例，启动预热（embedding/jieba/重排），避免首个请求承担加载；
- 检索是 CPU 计算 + 外部 LLM 调用，FastAPI 用线程池跑同步逻辑，SSE 不阻塞事件循环；
- 改写与 HyDE 并发执行，省一轮 RTT；
- 单 worker 部署（模型常驻内存），横向扩展建议把 embedding 拆成独立推理服务。

**C5. 怎么保证"线上跑的和评测跑的是同一套逻辑"？**
- 编排只有一份 `ChatService.answer()`，API、CLI、评测脚本都走它；
- 评测脚本用真实检索与真实 prompt，不另写一套；
- prompt 有版本号，trace 里记录本次用的版本。

### D. 评测与数据

**D1. 评测集怎么建的？**
- 40 条检索问题，按 type 分 keyword/paraphrase/multi_hop/noisy，每条标 gold_doc；12 条库外问题用于拒答评测；
- 语料是 19 篇原创企业文档（虚构公司"云策科技"），数字跨文档自洽（报销阈值、住宿标准、发布窗口……）；
- 诚实说明：这是自建小评测集，结论需要真实语料复核——但方法和脚本可直接复用。

**D2. 消融怎么做？**
- 固定同一份评测集与同一套 chunk，逐级叠加：BM25 → 向量 → 混合 → 改写 → HyDE → 重排；分块策略单独一组；
- 指标：文档级 Top-1/Top-3/MRR + 延迟分位；端到端另外看引用命中率、拒答率、token 成本；
- 详见 `docs/EVALUATION.md`。

**D3. 怎么衡量"幻觉"？**
- 构造 12 条知识库覆盖不到的问题（股价、竞品、隐私、未发布版本）；
- 正确行为是拒答，统计拒答率；同时看 in-scope 问题有没有被误拒（误杀率）；
- 自检是独立 judge + 证据，不是让模型自查。

**D4. 你做的东西有什么数据能证明有效？**
- 检索：Top-1 62.5%（BM25）→ 90%（混合+改写）；分块策略对比 80/85/78；
- 意图：96.2% 准确率（规则基线 59.9%），CPU 约 50ms/条；
- 端到端：P50/P95 延迟、平均 token、单次成本在 `eval/report-e2e.json`；
- 测试：100 个离线用例全绿；CI 可复现。

### E. 取舍与反思

**E1. 这个项目最大的难点是什么？**
- 不是某个算法，而是**把"能不能用"变成"可证明好用"**：检索参数、prompt、分块、重排每一个都可以说"我调好了"，但只有建评测集才能说清"好在哪、代价是什么"；
- 第二是**一致性**：一次问答涉及 5~6 个组件，任何一处降级或口径不同都会让评测失真，所以统一编排 + 统一 trace。

**E2. 如果重做，你会改什么？**
- 评测集扩大 + 引入真实企业语料，做统计显著性检验（现在 40 条，Top-1 差 2.5pt 就不可靠）；
- 检索层做语义缓存（相似问题复用），能显著降本；
- embedding/rerank 拆成独立推理服务，支持多副本。

**E3. 为什么不用 LangChain？**
- 链式抽象把"检索到了什么、为什么这么答"藏进黑盒，调试和讲解困难；
- 手写 3k 行业务代码，每一行都能解释；只用了 HTTP、numpy、jieba、rank_bm25、sentence-transformers；
- 代价：重复造轮子，生态里的回调/追踪能力要自己实现（已用 trace 补上）。

## 五、Agent 岗场景题（淘天 / 字节风格，常在大厂一面出现）

> 这些题不考"记得什么框架"，考"你能不能把项目经验迁移到新场景"。每题都用本项目做锚点，再给扩展思路。

**S1. 为什么把传统 RAG 改造成 Agentic RAG？传统 RAG 的痛点？**
- 传统 RAG 是"单次检索 → 生成"的流水线：检索被动、一次性，多跳问题只命中一半，证据不足时要么硬答要么答偏；
- Agentic 把检索交给 Agent 主动驱动：检索 → 判断证据是否充分 → 不足则带缺口反馈改写再查 → 够或到上限才生成；
- 本项目的 `judge` 输出 `{sufficient, missing}`，`missing` 作为下一轮查询生成的输入——这是闭环修正的引擎；
- 兜底：`max_rounds` 上限 + 达上限用末轮证据诚实作答，不无限检索。
- 代码：`app/agentic/agentic_rag.py`。

**S2. Search 和 Read 工具怎么配合？**
- `kb_search` 返回带 `doc_id` 的片段（粗定位）；`kb_read` 按 `doc_id` 展开全文（精读）；
- 分工的理由：一次把全文塞进上下文会挤爆窗口，先看摘要再读全文更接近人的查资料方式；
- 工具描述里明确写了"先 search 再 read"的使用边界，降低误用。

**S3. 为什么不用 LangChain？状态做成图节点了吗？**
- 自研理由：链式抽象把中间过程藏起来，调试和讲解都困难；本项目业务代码约 4k 行，每一行都能解释；
- 状态没有做成图：当前链路是"记忆 → 路由 → 检索 → 自检"的线性流程，用显式的 result 对象记录；
- 什么时候需要图/状态机：多分支并行、需要回退重试、需要断点续跑时——这是扩展点，不是当前缺陷。

**S4. 为什么自研"向量 + BM25 + RRF"，而不是直接上 Elasticsearch？**
- ES 的"全文检索 + kNN + 融合"在能力上等价，但引入 ES 意味着多一套集群、多一套运维；
- 本项目规模（75 块 / 可扩展到 10 万级）用 numpy 精确检索 + rank_bm25 就够，延迟 <20ms；
- 规模决定选型：百万级以上或需要按租户隔离时，换 Qdrant/Milvus + ES，接口已抽好（`BaseVectorStore`）。

**S5. 如果让你为淘宝研发构建"研发上下文知识库"，怎么做？**
- 三类异构数据分开处理：文档（制度/设计稿）走文本分块 + RAG；代码走函数/类粒度索引（可加代码图谱）；日志/告警走时序检索；
- 分层检索：高频问答 RAG；跨文件关系用代码图谱（GraphRAG 思路）；日志按时间窗检索；
- 统一路由层：先判断问题类型，再选检索器——复用本项目的意图路由思想；
- 质量闭环：入库抽检 + 检索命中率回灌 + 低置信度样本进迭代清单。

**S6. 设计一个"需求 → 拆解 → 方案 → 代码"的研发 Agent，关键要素？**
- 输入质量：先做需求澄清（对 PRD 提问、补缺），再进流水线；
- 上下文供给：相关代码/历史方案/规范要先检索到（复用本项目 RAG）；
- 拆解与编排：大任务拆成可验证子任务，每步有明确产出与检查点；
- 验证闭环：生成后编译/跑测试/自检，失败回退（复用本项目的自检思想）；
- 可控性：关键节点留人审闸门，不追求一步端到端。

**S7. 设计"PDF 论文 → 结构化抽取"的 Pipeline？**
- 解析：版面分析（表格/双栏/图注）→ 阅读序重排 → 文本；页眉页脚过滤、跨页段落拼接；
- 结构化：按目标 schema（如 PICO）让 LLM 输出 JSON；抽取结果与原文不一致就重抽（自检思想）；
- 入库：结构化字段 + 原文 chunk 都进检索库，支持"按字段问答"与"按原文溯源"两种检索；
- 评测：字段级准确率 + 引用可溯源性，而不是只看"看起来像"。

**S8. 项目迭代怎么做得有章法？**
- 每个模块先有评测集（检索 40 条、意图 22 条/类），改动前后量化对比；
- 误判/漏检样本就是迭代清单（意图从规则到 TinyBERT 就是靠失败样本驱动）；
- 线上信号：低置信度、超轮数、自检拦截、用户点踩，都是下一轮改进的输入。
