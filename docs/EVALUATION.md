# 评测报告

> 所有数字都由仓库内的脚本产生，可一键复现：`make eval`（约 6 分钟，需要 API Key；无 Key 时端到端部分会走 Mock，检索与意图评测不受影响）。
> 原始数据：`eval/report-retrieval.json`、`eval/report-bench.json`、`eval/report-e2e.json`、`eval/report-intent.json`。

## 1. 评测设置

| 项 | 说明 |
| --- | --- |
| 语料 | 19 篇原创中文企业文档（虚构公司「云策科技」），6 大类，共约 2 万字 → 75 个检索块 |
| 检索评测集 | 40 条人工撰写：keyword 14 / paraphrase 16 / multi_hop 6 / noisy 4，每条人工标注 gold_doc |
| 拒答评测集 | 12 条知识库覆盖不到的问题（股价、竞品、隐私、未发布版本等） |
| 意图数据集 | train 660 / eval 132，6 类各 110 / 22 |
| 指标 | 文档级 Top-1 / Top-3 / MRR（命中 gold_doc 即算，不要求命中具体块）；延迟 P50/P95 |
| 硬件 | 48 核 CPU / 121GB 内存，无 GPU；embedding 与重排均跑在 CPU |
| 模型 | 生成/改写：`deepseek-v4.1-flash`（网关）/ `deepseek-v4-flash-fast`（辅助任务）；embedding：`bge-small-zh-v1.5`；重排：`bge-reranker-base` |

## 2. 检索消融（同一评测集、同一批块）

| 配置 | Top-1 | Top-3 | MRR | P50 | P95 |
| --- | --- | --- | --- | --- | --- |
| BM25（关键词） | 62.5% | 85.0% | 0.749 | 0.5 ms | 1.6 ms |
| 向量（bge-small-zh） | 85.0% | 100% | 0.917 | 17.3 ms | 24.9 ms |
| 混合 + RRF | 85.0% | 92.5% | 0.893 | 16.7 ms | 24.9 ms |
| + 查询改写 | **90.0%** | 100% | 0.938 | 654 ms | 1.2 s |
| + HyDE | **92.5%** | 100% | 0.958 | 3.55 s | 4.4 s |
| + Cross-Encoder 重排 | 90.0% | 100% | 0.950 | 3.09 s | 3.5 s |

### 分题型看，混合检索补的正是短板

| 配置 | keyword | paraphrase | multi_hop | noisy |
| --- | --- | --- | --- | --- |
| BM25 | 85.7% | **31.3%** | 83.3% | 75.0% |
| 向量 | 100% | 68.8% | 100% | 75.0% |
| 混合 + RRF | 100% | 62.5% | 100% | 100% |
| + 查询改写 | 100% | **81.3%** | 100% | 75.0% |

**读法**：
- 关键词检索对"口语化改写"几乎无能为力（paraphrase 31%）；
- 向量检索补上语义，但会稀释部分精确匹配（keyword 从 85.7% 到 100% 反而更好，说明本语料关键词不重复、语义匹配占优）；
- 查询改写是 paraphrase 类从 62.5% → 81.3% 的关键一步——把口语化问题改写成文档用词；
- 混合的 Top-3 一度低于纯向量（92.5% vs 100%），因为 RRF 会奖励"两路都出现"的文档，可能把某一路排第 1 的正确文档挤到第 2/3 —— 这也是后面保留重排位的原因。

## 3. 分块策略对比（同一检索配置）

| 策略 | 块数 | Top-1 | Top-3 | MRR |
| --- | --- | --- | --- | --- |
| 固定窗口 500/60 | 72 | 80.0% | 97.5% | 0.874 |
| **递归（默认）** | 75 | **85.0%** | 92.5% | 0.893 |
| 语义分块 | 76 | 77.5% | 97.5% | 0.863 |

结论：在 800~1000 字的短文档上，语义分块切得太碎（句级断点），反而损失上下文；递归分块（标题→段落→句子）在"块大小可控"与"语义完整"之间最好。更长、结构更松散的文档可能需要重新评估。

## 4. 意图分类

| 分类器 | 准确率 | Macro-F1 | 单条延迟 |
| --- | --- | --- | --- |
| 规则（关键词 + 槽位） | 59.9% | 0.541 | 0.002 ms |
| **TinyBERT 微调（默认）** | **96.2%** | 0.962 | 52 ms |

- 训练：660 条、8 epoch、CPU 95 秒；模型 11M 参数（~45MB）；
- 易混样本（"现在几点" vs "上班时间几点"）已刻意放进评测集，用来验证边界；
- 规则分类器是降级路径：无 torch/未训练模型时自动启用，保证路由永远可用。

## 5. 端到端（真实模型）

| 指标 | fast 模式 | quality 模式 |
| --- | --- | --- |
| 样本 | 20 条 in-scope（前 14 keyword + 前 6 paraphrase） | 40 条 in-scope + 12 条 OOS |
| 引用命中率 @1 | 90.0% | 85.0% |
| 引用命中率 @3 | 90.0% | 97.5% |
| 库外问题拒答率 | 83.3% | **100.0%** |
| 延迟 P50 / P95 | 4.6s / 6.6s | 10.4s / 14.5s |
| 平均 token / 次 | 2608 | 5433 |
| 平均成本 / 次 | $0.00043 | $0.00092 |

按题型（quality 模式，citation 命中率）：

| 题型 | n | @1 | @3 |
| --- | --- | --- | --- |
| keyword | 14 | 100% | 100% |
| paraphrase | 16 | 69% | 94% |
| multi_hop | 6 | 100% | 100% |
| noisy | 4 | 75% | 100% |

**读法**：
- 自检带来的收益很直观：库外拒答率 83% → **100%**，代价是平均多花约 2.1 倍成本、延迟翻倍；
- 引用命中率 @3 达到 97.5%：40 条问题里 39 条能在前 3 条引用中找到正确文档；
- paraphrase 类仍是短板（@1 69%），与检索消融一致——这类问题需要改写，而 quality 模式的改写对口语化仍不够；
- 延迟包含真实网关耗时，评测期间网关延迟在 0.5~8s 波动，所以这里给分位数而不是平均值。

（本节数据由 `python scripts/eval_e2e.py` 生成，原始明细见 `eval/report-e2e.json` / `report-e2e-fast.json`。）

## 5.1 延迟拆解（`scripts/bench.py`）

| 链路 | P50 | P95 | 主要耗时 |
| --- | --- | --- | --- |
| fast（双路召回 + 融合） | 18.9 ms | 21.5 ms | 向量检索 ~17ms，BM25/融合 <1ms |
| quality（+ 查询改写） | 674 ms | 1.39 s | 改写 651ms（一次 LLM 调用） |
| quality + 重排 | 698 ms | 1.29 s | 重排模型加载后每查询 +1.5s 左右 |

> 检索本身是毫秒级的；端到端延迟主要来自 LLM 生成与自检，而不是检索算法。

## 6. 三个"负结论"（面试重点）

1. **HyDE 只带来 +2.5pt，却把检索从 0.65s 拖到 3.5s** → 默认关闭，保留开关；
2. **Cross-Encoder 重排在本语料上 -2.5pt**（RRF 已经把正确文档排到前面，重排反而被短片段干扰）→ 默认关闭；换长文档语料可重跑消融再决定；
3. **语义分块不如递归分块**（77.5% vs 85%）→ 默认递归。

这三条比"我又加了三个优化"更能说明：**所有默认值都是数据决定的，不是跟风。**

## 7. 复现方式

```bash
make seed     # 重建索引
make eval     # 检索消融 + 端到端 + 分块对比(写 eval/report-*.json)
make bench    # 延迟基准(含开启重排的对比)
python scripts/train_intent.py && python scripts/eval_intent.py   # 意图分类
```

## 8. 局限

- 40 条评测集的统计功效有限（Top-1 差 2.5pt 可能不显著），结论需要更大规模评测复核；
- 语料是自建虚构企业文档，与真实企业语料（长文档、表格、扫描件、跨系统链接）差异明显；
- 延迟数据是单机空载测量，不包含并发排队；
- LLM 版本的网关性能波动会影响改写/HyDE 的延迟数字，但检索指标不受影响。
